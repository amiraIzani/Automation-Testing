Otomasi Pengujian OPEL Modul HSS Safety

Otomasi end-to-end untuk 19 halaman modul HSS Safety aplikasi OPEL: navigasi lewat menu sidebar (dashboard → HSS → Safety → Reporting/Transaction), setiap tab dibuka, setiap tombol diklik — di setiap tab — dan setiap fitur transaksional dicoba sungguhan: create, edit, export, import (file dummy dipasang tanpa dikirim ke server), sampai delete. Seluruh hasil dirangkum menjadi satu laporan ini.

Ringkasan Eksekutif

Proyek ini membangun dan menjalankan otomasi pengujian berbasis Selenium untuk modul HSS Safety aplikasi OPEL (Superadmin). Tujuannya tiga:

  • memastikan seluruh fitur di setiap halaman berfungsi — bukan sekadar halaman terbuka, melainkan setiap tab dibuka dan setiap tombol diklik;
  • mendokumentasikan perilaku aplikasi DEV apa adanya, termasuk penyimpangan dari harapan (menjadi umpan balik bagi tim pengembang);
  • menjadi dasar regression test berkala yang bisa dijalankan ulang kapan pun aplikasi berubah.

Cakupan: 19 halaman Safety (5 Reporting, 11 Leading Indicator, 3 Lagging Indicator) dengan 45 kasus uji. Seluruh kasus kini berstatus ✓lulus — 44 lulus langsung pada full run 31 Agustus 2026, 1 kasus (Incident Investigation) diperbaiki pada hari yang sama dan diverifikasi ulang; 1 kasus lain yang sempat flaky pada run parsial sesi panjang (Master Alat Create) juga diverifikasi ulang hijau — efektif 45/45.

Arsitektur Otomasi

2.1 Pendekatan

Framework memakai pola Page Object Model (POM): setiap halaman aplikasi punya satu kelas yang menyimpan locator dan aksi halaman itu, sehingga test membaca alur bisnis — bukan koordinat elemen. Locator memakai atribut stabil hasil scan langsung dari website (kolom grid th[data-name], id toolbar, teks tombol), bukan posisi yang mudah berubah.

  • 1 sesi browser untuk seluruh suite — Chrome dibuka sekali, login otomatis lewat profil dengan sesi Azure AD B2C aktif, ditutup di akhir (pola warisan proyek NewDLA).
  • Menunggu, bukan menebak — semua sinkronisasi memakai WebDriverWait terhadap indikator nyata (overlay Processing, modal terbuka, tabel tampil); jeda sleep hanya untuk pacing visual.
  • Handal terhadap quirk SPA — navigasi ulang otomatis bila halaman "stuck", retry klik, dan pembersihan draft lokal (localStorage) bawaan aplikasi.

Alur Pengujian

3.1 Alur Satu Sesi Suite (End-to-End)

  1. Login otomatisChrome dibuka dengan profil bersesi Azure AD B2C — 1 redirect langsung ke dashboard, tanpa isi form.
  2. Navigasi menuMulai dari dashboard → sidebar HSS → Safety dibuka, lalu sub Reporting dan Transaction dibuka satu per satu — link halaman diverifikasi muncul (sidebar bersifat accordion dan memuat judul menu duplikat, ditangani dengan rantai menu berjenjang).
  3. View 19 halamanSetiap halaman dibuka, tabel DataTables diverifikasi benar-benar tampil dengan data.
  4. Alur menu per halamanTest Halaman Lengkap membuka halaman lewat klik link di menu sidebar (bukan URL langsung) — dashboard → HSS → Safety → Reporting/Transaction → link halaman.
  5. Tab internal14 tab di 4 halaman dibuka satu per satu dan diverifikasi menjadi aktif; toolbar dicek dan seluruh tombol fitur dijalankan di setiap tab (kecuali tombol pembuat data dan Cancel, yang dijalankan di tab utama).
  6. Tombol toolbarTombol yang diharapkan tampil di tiap halaman diverifikasi benar-benar ter-render di setiap tab (daftar per halaman hasil scan).
  7. Coba semua tombolSetiap tombol DIKLIK sesuai fungsinya — Import membuka modal lalu file dummy dipasang pada input upload (tanpa dikirim), Export mengunduh file, Create membuat data dummy, Columns dibuka lalu item Settings diklik, FullScreen masuk-keluar.
  8. Transaksi mendalam3 halaman Lagging diuji penuh: edit grid inline + Submit, filter tanggal/unit, export, import template. Master Alat: create dummy & delete.
  9. LaporanKotak hasil per label dicetak di akhir sesi; report.html + screenshot otomatis setiap kegagalan.

3.3 Keamanan Data DEV

Pengujian transaksional tidak merusak data produksi DEV: setiap perubahan di-revert ke nilai awal, dummy dibuat dengan penanda unik untuk verifikasi tepat sasaran, dan file dummy pada modal Import hanya dipasang pada input tanpa pernah dikirim ke server (tombol Import tidak diklik). Fitur yang memang tidak ditawarkan aplikasi (mis. Reload Data tersembunyi, delete yang tidak commit — lihat §6) diverifikasi elemennya tanpa dipaksa.

Kesimpulan & Rekomendasi

7.1 Kesimpulan

  • Cakupan penuh tercapai: 19 halaman Safety + 14 tab internal diuji; navigasi dilakukan lewat menu sidebar (dashboard → HSS → Safety → Reporting/Transaction) dan setiap tombol toolbar diklik — di tab utama maupun di setiap tab internal — sesuai standar "test menyentuh fitur, bukan sekadar membuka halaman".
  • 45 dari 45 kasus uji hijau (44 lulus full run 31-08 + 2 verifikasi ulang pasca-perbaikan), dijalankan dalam satu sesi browser end-to-end, siap diulang kapan pun sebagai regression test.
  • Data DEV terjaga: semua perubahan di-revert, dummy ber-penanda unik, file dummy pada modal Import hanya dipasang pada input tanpa pernah dikirim ke server.
  • 10 perilaku aplikasi menyimpang terdokumentasi lengkap dengan bukti probe — menjadi umpan balik konkret bagi tim pengembang.
  • Otomasi tahan perubahan data: anchor grid dicari dinamis (bulan dengan data terisi), navigasi menu tahan terhadap accordion & judul duplikat, dan perilaku aplikasi yang berubah otomatis membunyikan alarm lewat assert.

7.2 Rekomendasi

Untuk Tim Pengembang

  • Verifikasi temuan §6, terutama delete yang tidak commit dan edit Statistic yang tidak tersimpan — keduanya berpotensi bug data.
  • Periksa export Incident Investigation yang tidak menghasilkan file.
  • Konfirmasi apakah penyembunyian tombol Reload Data di 18 halaman memang disengaja.
  • Konfirmasi apakah perilaku dropdown Columns (Unfreeze/Settings, bukan toggle kolom standar) sudah sesuai desain.

Untuk Otomasi

  • Pantau flakiness sesi panjang (Incident, Master Alat Create) — bila berulang, pertimbangkan me-refresh sesi browser per kelompok halaman.
  • Perdalam uji halaman Leading Indicator (edit inline di Static/Monthly Report selain Lagging).
  • Jadwalkan full run berkala dan perhatikan alarm perilaku aplikasi (assert yang menunggu perubahan perilaku).
  • Perluas ke modul OPEL lain (HSS non-Safety) dengan pola page object yang sama.
